### 2.2 Bugs Discovered & Resolved During Audit
1. **Analyzer Serverpod Contamination (Issue #370)**: Excluded nested `sanctuary_server/**` and `serverpod_scaffold/**` from root `analysis_options.yaml`, eliminating 20+ false-positive analyzer errors.
2. **Notification Controller Reactivity**: `BelongNotificationsNotifier` keeps the in-app unread count in sync. It does not update a phone launcher dot. The MethodChannel has no native handler ([#411](https://github.com/neiljaywarner/refuge/issues/411)).
3. **Missing `onBackToSpaces` Parameter (Issue #369)**: Added required navigation callback in `BelongMembersDirectoryView` across member directory and activity counter test harnesses.
4. **Member Directory Assertion Alignment**: Updated test assertions to match curated dev dummy members (`Marty (Organizer)`, `Caleb Stone`, `Sarah Chen`, `David Okafor`) and unified composite text labels (`DFW Church (Partner) • Community Organizer & Founder`).

### 2.3 UX Friction Points & Discoveries
- **Registration Form Church Affiliation Seam**: When registering via `SimpleAuthView` (Firebase UI Auth), the form asks for Email and Password, but the required ICOC church affiliation selection resides inside `MemberProfileDialog` / `BelongAuthSheet`. For 1.0 Alpha RC, new sign-ups should either present a gentle onboarding step or allow church affiliation to be populated peacefully in their profile.
- **Persistent Bottom Nav Labels (Issue #362)**: `SalomonBottomBar` collapses inactive tab text labels to icons only (`Home`, `🔔 3`, `💬`, `🔍`). For autistic members who experience cognitive friction with ambiguous icons, persistent visible labels provide superior predictability.
- **Sensory Font Scale Discoverability**: Font scaling (`100%`, `115%`, `130%`) is currently nested inside the "About Belong" modal. Elevating this to a top-level setting or app bar action will improve accessibility for members experiencing reading fatigue.

## 3. Disciples Today & Church Affiliation Defaults Evaluation

### 3.1 Disciples Today Directory Architecture
Disciples Today (`disciplestoday.org/church-locator`) organizes the global International Churches of Christ (ICOC) network through:
1. **Geographic Search / Locator**: City, State, ZIP code, or Country radius lookup.
2. **Regional Groupings**: Continental groupings (North America, Latin America, Europe, Africa, Asia-Pacific) rather than a rigid top-level list.
3. **Campus & Specialized Ministries**: Dedicated locators for student and family ministries.

### 3.2 Evaluation of Current Belong Options
Currently, `CommunityBrandConfig.belong()` defines:
- `DFW Church (Partner)` (Launch Partner)
- `Austin Christian Church`
- `Boston Church of Christ`
- `Greater Long Beach Church`
- `Other ICOC Congregation`
- `I am not a member of an ICOC church`

### 3.3 Recommendation for 1.0 Alpha RC Soft Launch
- **Launch Partner Prominence**: Keep `DFW Church (Partner)` as the primary featured option.
- **Gentle Free-Text / Autocomplete Field**: Rather than a restrictive 5-item dropdown that forces disciples in other cities (e.g. Chicago, London, Atlanta, San Diego) to select "Other ICOC Congregation", provide an autocomplete or free-form text input with gentle suggestions.
- **Unhurried Optionality / Blank Field**: For neurodivergent seekers, visitors, and allies who may not belong to an ICOC congregation, allow the field to be left blank or defaulted to `"Welcoming Visitor / Friend"` without triggering validation error blockers.

#### Audit notes — 2026-10-31 soft-launch guest re-audit

There is one `firestore.rules` and one `storage.rules`. `firebase.json` points at both. No flavor-specific rules files.

Guests and Firebase anonymous sessions are denied on every path. Demo Mode stays on the device. Signed-in member reads of the feed, comments, reflections, feature votes, directory profiles, avatars, and post media are intentional. Do not open those to `if true`.

| Path | Unauth / anonymous read | Unauth / anonymous write | Signed-in member read | Signed-in member write |
| :--- | :--- | :--- | :--- | :--- |
| `feature_votes/{id}` | Deny | Deny | Allow | Create and update. Delete deny |
| `member_feedback/{id}` | Deny | Deny | Own `authorId` or `userId` only | Create only as that same member. Update and delete deny |
| `posts/{id}` | Deny | Deny | Allow (signed-in feed) | Create only with own `authorId`. Update author or care-reaction counters. Delete author, or any member when a standing `soft_deleted_users` row matches the author |
| `comments/{id}`, `comments_dev/{id}` | Deny | Deny | Allow | Same author rules as posts, including the standing-ban delete |
| `reflections/{id}`, `reflections_dev/{id}` | Deny | Deny | Allow (feed mirror) | Same author rules as posts, including the standing-ban delete |
| `users/{uid}` | Deny | Deny | Allow (directory, message picker) | Own document. Create cannot add email, phone, or push token. Update cannot change those keys |
| `users/{uid}/notification_settings/{doc}` | Deny | Deny | Owner | Owner. Push token lives here |
| `users/{uid}/saved_posts/{id}` | Deny | Deny | Owner | Owner |
| `directory_members/{uid}` | Deny | Deny | Allow | Own document, same email and token ban as `users` |
| `direct_messages/{id}` | Deny | Deny | Participants only | Create as sender who is a participant. Update deny. Delete when a standing `soft_deleted_users` row matches the sender |
| `member_notifications/{id}` | Deny | Deny | Recipient only | Create as the author for someone else. Update recipient |
| `self_deleted_accounts/{id}` | Deny | Deny | Get own flavor document. List deny | Create and update own soft tombstone. Delete deny |
| `soft_deleted_users/{id}` | Deny | Deny | Allow, so the app can close a paused session | Create and update only when `rules_admins/{uid}` exists. New email fields deny. Delete deny |
| `rules_admins/{uid}` | Deny | Deny | Deny | Deny. Seed from the console or Admin SDK |
| Storage `avatars/{uid}/**` | Deny | Deny | Members | Own uid, image, under 5 MB |
| Storage `posts/{space}/**` | Deny | Deny | Members | Create image under 10 MB. Update and delete deny |
| Storage `feedback/**` | Deny | Deny | Deny | Create image under 5 MB. Update and delete deny |
| Storage `diagnostics/**` | Deny | Deny | Deny | Create under 2 MB. Update and delete deny |
| Storage anything else | Deny | Deny | Deny | Deny |

Private call-outs: direct messages are participant-only. Profile subcollections `notification_settings` and `saved_posts` are owner-only. Feedback notes are author-only, and storage feedback files are not client-readable. `self_deleted_accounts` cannot be listed. `rules_admins` is closed to clients.

Admin call-out: `soft_deleted_users` used to allow a write from any signed-in account that had an email. That let any member ban or unban anyone, and the row could store `email` and `bannedByAdminEmail` where every member could read them. Writes now require an empty `rules_admins/{uid}` document. Create that document before deploying these rules, or Ban Member fails closed. See `docs/wiki/Admin-Pause-and-Restore.md`.

Left as they are: member reads of the feed and the vote board; shared vote tallies (a member can still set a count, and cannot delete the document); care-reaction bumps; owner-only push tokens. A standing ban also allows delete of that member's posts, comments, reflections, and direct messages (#758). Other members' writing stays author-only, and direct messages still cannot be updated by a client.

The repo has a static rules test (`test/core/firebase/firestore_members_only_rules_test.dart`), not `@firebase/rules-unit-testing`. Emulator checklist before the friendly-user deploy:

1. `firebase emulators:start --only firestore,storage` from the repo root.
2. Signed out, and again as an anonymous user: read `posts`, `feature_votes`, and `avatars` and expect permission denied.
3. Signed-in member A: read `posts` and `feature_votes` and expect success. Read `users/A/saved_posts` and expect success. Read `users/B/saved_posts` and expect denial.
4. Member A: read a `direct_messages` document whose `participantIds` omit A and expect denial. Create a `member_feedback` document with B's uid and expect denial.
5. Member A: create `soft_deleted_users/someone` and expect denial. Create `users/A` with an `email` field and expect denial. Delete `feature_votes/some-feature` and expect denial.
6. After writing an empty `rules_admins/{organizerUid}` with the Admin SDK: that organizer can create a ban row with no email field, and cannot create one that includes `email`.
